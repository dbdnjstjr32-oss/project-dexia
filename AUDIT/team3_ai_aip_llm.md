# Team 3 Audit — AI brain / AIP logic / agents / LLM integration

Scope: `dexia/ai/`, `dexia/aip/`, `dexia/agent/`, `dexia/api/llm_gateway.py`, `run_e2e_proof.py`, and the evidence `*.jsonl`.
Date: 2026-06-21. Method: read the full call chain end-to-end + inspected the evidence artifacts for realism.

---

## VERDICT ON PROOF HONESTY: **PARTLY — the live LLM is real, but the e2e "kill-chain proof" does NOT prove the LLM closes the chain.**

Two independent facts, both verified:

1. **The LLM inference itself is genuinely real.** `llm_audit.jsonl` (429 rows) shows real local Ollama calls: variable latency (452 ms – 64.8 s), real prompt/completion token counts, model swaps (`llama3.1:8b` → `qwen2.5:7b`), and a genuine transport failure (`wsarecv: An existing connection was forcibly closed`, status 500). This is not templated. The 5 calls on 2026-06-21 around the last proof run are real (one error at 05:20, then 4 OK calls 1.8–50.6 s). **There is NO mock/stub fallback on the live tactical path** (`llm_gateway.py`, `mission_manager.py`): on any LLM error the gateway returns `{"ok": False}` and the loop logs `"AIP 연결 불가"` — it does not fabricate a COA.

2. **But `run_e2e_proof.py` proves a *commander-scripted* kill, not an *LLM-decided* one.** The kill that the proof asserts comes from `MissionManager.command_fires()` (a pure ActionBus path with **zero LLM involvement**), triggered by the hardcoded `COMMANDER ORDER` block at `run_e2e_proof.py:153-159`. Every LLM-proposed COA in the actual proof run was **rejected** (`e2e_proof_log.jsonl`: `COA-002`, `COA-003` → "Rejected"; the kill is `CMD-001`, "Commander-directed fire mission"). The pass/fail checks (`run_e2e_proof.py:178-188`) require only `detect_tick`, `fire_tick` (set by `command_fires`), and the ground-truth `armor.alive` flag — **none of them require, inspect, or depend on any LLM output.** The proof passes identically whether the LLM returns a brilliant COA, an empty COA list, or nothing at all (errors are swallowed and the script proceeds to the scripted commander order). So the headline artifact does not demonstrate the AIP/LLM closing a kill chain; it demonstrates the *physics + ActionBus + fusion* closing one under human command.

Additional honesty problem: the other two "evidence" files in scope, **`reasoning_trace.jsonl` and `scenario_evals.jsonl`, contain NO LLM output at all** — they are produced by the deterministic `policy.decide` rule engine via `MissionRunner` (`loop.py` docstring line 9: *"No LLM is required"*). `reasoning_trace.jsonl` has no `model`/`llm` field; its `reasoning` strings are hardcoded f-strings from `MissionRunner._narrate()`. And the AIP self-correction memory (`episodic_memory.jsonl`) is **dominated by `"llm": "mock"` episodes** (24 of 25 rows), i.e. the doctrine loop was mostly exercised with the hardcoded `MockLLMClient`, not the real model.

So: the LLM is wired and really runs on the *live browser/command-server loop*, but the artifacts a reviewer would point to as "proof the AI brain works" either bypass the LLM (e2e proof, reasoning_trace, scenario_evals) or were generated by a mock (episodic_memory). The mandate ("a REAL LLM + physics + ground-truth kill-chain proof, NO mocked/PPT-style proofs") is **not met by `run_e2e_proof.py` as written.**

## CRITICAL

### C1 — e2e "kill-chain proof" passes without the LLM ever making the kill decision
`run_e2e_proof.py:153-159` (commander order) + `:178-188` (verification).
The lethal action is `mm.command_fires(trk.track_id, arty.entity_id)` — a deterministic ActionBus path with no LLM call. The verification dict checks detection (sensor), `fire_tick` (set by the scripted commander order), and ground-truth death; it never asserts that an LLM-proposed COA was the thing approved/executed. In the captured run (`e2e_proof_log.jsonl`) the LLM's COAs were all *rejected* and the kill is `CMD-001`. **Blast radius:** the project's central honesty artifact certifies "CHAIN PROVEN" while the AIP brain is decorative for the kill decision. A model that is completely broken (empty COAs, all errors) still yields a green proof. This is the exact "fake-proof" failure mode the mandate warns against — not via a code mock, but via a verification harness that doesn't test what it claims.

### C2 — `LLMGateway.available()` reports availability from a *package import*, not a reachable model
`llm_gateway.py:63-64` (`return self._ollama is not None`), gating `run_e2e_proof.py:96-98`.
`available()` is True whenever the `ollama` Python package imports and a client object constructs — even if the Ollama daemon is down or the model is not pulled. The proof's only "is the LLM live?" guard (`if not mm.llm.available(): return 1`) therefore passes on a machine with **no model loaded**. The actual chat then fails with `{"ok": False}`, the loop logs an ERROR, and the **scripted commander path still drives the kill to a PASS** (see C1). Net effect: the one gate meant to enforce "honest live proof" is satisfied by an importable library, not a working model. **Blast radius:** "honest live proof" can be produced on a box where the LLM never answered a single token.

## HIGH

### H1 — In-scope evidence artifacts have no LLM provenance yet are presented as AI reasoning
`reasoning_trace.jsonl` (16 rows, keys: no `model`/`llm`; `reasoning` = `loop.py:163-167` f-strings) and `scenario_evals.jsonl` (written by `campaign.py:27` → `MissionRunner` → `policy.decide`).
`loop.py` is explicitly LLM-free ("No LLM is required; an optional gateway can narrate"). The `decisions`/`reasoning` are 100% from the deterministic `policy.decide` (`policy.py`). These files are the natural "look, the AI reasons about the battlefield" exhibits, but they contain zero model output. **Blast radius:** anyone auditing realism by sampling these `.jsonl` files is looking at a rule engine's output mislabeled as AI reasoning.

### H2 — AIP doctrine self-correction loop ran almost entirely on the MockLLMClient
`logic_blocks.py:89-120` (`MockLLMClient.complete` ignores the prompt, returns a hardcoded root-cause/CoT) and `:123-155` (`OllamaLLMClient` silently falls back to the mock on `not self._ok`, `not resp.ok`, or any exception).
`episodic_memory.jsonl`: 24/25 episodes are `"llm": "mock"`; only one (2026-06-04T05:49) is `"llm": "ollama"`. The mock literally string-matches the splash radius out of the prompt and emits a canned diagnosis. Because `OllamaLLMClient.complete` catches *all* exceptions and substitutes the mock, a doctrine update that *looks* AI-authored can be entirely canned, and the episodic memory does not visibly distinguish a degraded run. **Blast radius:** the "AI learns doctrine from failures" capability (recipes.json v1.0→1.1) is, in the recorded history, overwhelmingly a deterministic template, not LLM reasoning — yet it persists into `recipes.json` and feeds future runs (state divergence risk).

### H3 — Live tactical loop silently degrades to "no decision" and the run continues
`mission_manager.py:244-247` (`if not res.get("ok"): append ERROR; return`) and `:262-265` (JSON parse failure → ERROR feed entry, return).
Any LLM failure (timeout, circuit-open, 500, malformed JSON) makes `_orient_and_decide` return with **no COA** and the OODA loop proceeds as if the AIP simply had nothing to say. Combined with `run_cycle` only invoking the LLM on tick 1 or when a brand-new track appears (`mission_manager.py:355-356`), a single dropped call at the wrong moment means the AIP never re-proposes for that engagement — the human (or, in the proof, the scripted commander) carries it. There is no retry, no surfaced "the brain is offline" hard-stop on the live path; failure is indistinguishable from "AIP chose to do nothing." **Blast radius:** in the live game the AIP can appear to "work" while quietly contributing nothing for long stretches.

### H4 — Circuit breaker is process-global mutable state shared across all missions/sessions
`llm_gateway.py:23-24, 81-137` (`_cb_failures`, `_cb_open_until` are module globals; `get_gateway()` returns a process-wide singleton at `:170-177`).
Three consecutive failures open the breaker for 60 s **for every caller in the process** — every concurrent WebSocket session, the doctrine AAR, and any eval all share one breaker. One flaky mission can blind the AIP for all sessions; conversely the state is not reset between `run_e2e_proof.py` invocations within a long-lived process. **Blast radius:** cross-session interference and non-deterministic proof behavior depending on prior process history.

## MEDIUM

### M1 — Unbounded/untrusted scenario text flows straight into the prompt with no sanitization
`mission_manager.py:212-242` (tracks + blue assets `json.dumps`'d into the prompt) and `:217-218` (`COMMANDER MODIFICATION: {user_modification}` — raw commander chat from the WebSocket `MODIFY` handler, `command_server.py:147-149`).
Commander free-text and scenario-derived strings are concatenated into the prompt with no escaping or length bound. There is no prompt-injection mitigation. The saving grace is that the *output* side is whitelist-validated (see strengths), so injection can mislead the model but cannot directly execute an arbitrary action — it could, however, get the model to emit a valid-but-wrong COA (e.g. fire on a friendly-adjacent track). **Blast radius:** model can be steered by injected scenario/chat text; bounded by output validation, not by input hygiene.

### M2 — Brittle JSON parsing of model output; one of two divergent parsers
`mission_manager.py:249-265` hand-rolls code-fence stripping + `json.loads(strict=False)`; `blocks.py`/`tactical_agent.py` use `_extract_tools_from_text` (`tactical_agent.py:29-53`). Two different parsing strategies for "model emitted JSON-as-text" exist, and the mission-manager one only strips a leading ```` ```json ```` / trailing ```` ``` ````; any prose around the JSON, or a second JSON object, makes the whole COA batch silently drop (caught at `:262`, logged, discarded). **Blast radius:** valid model intent lost to formatting; inconsistent behavior between the two AIP entry points.

### M3 — Schema of the model's COA JSON is never validated as a whole, only field-by-field after the fact
`mission_manager.py:281-325` (`_validate_coa`) coerces `confidence`/`expected_success` with `float(... or 0.0)` and accepts arbitrary `description`. A model returning `confidence: "high"` silently becomes `0.0`; there is no JSON-schema gate, so partially-malformed COAs are massaged rather than rejected, and the numbers the commander sees (P_success) may be fabricated zeros rather than model estimates. **Blast radius:** the HITL card can show misleadingly low/զero confidence that the model did not actually express.

### M4 — `_est_loss`/`_p_kill`/`generate_coa_options` ranking is fully deterministic and labeled "AIP 타격 방안"
`mission_manager.py:492-583`. The ranked 안1/안2/안3 strike options shown to the commander as the "AIP recommendation" are computed by closed-form heuristics (`_p_kill`, `_est_loss`) with **no LLM input**. This is reasonable engineering, but it is surfaced in the UI feed as the AIP's tactical recommendation, blurring the line between LLM reasoning and a scoring formula. **Blast radius:** reviewers may attribute deterministic scoring to "the AI brain."

## STRENGTHS (verified — give credit where due)

- **No `eval`/`exec`/`pickle`/dynamic import on model output or recipes** anywhere in scope (grep over `dexia/`): zero matches. Prompt-injection → code-execution is **not** possible.
- **COA execution is whitelist-gated**: `_validate_coa` (`mission_manager.py:281-314`) only accepts actions in `ACTION_REGISTRY`/`TOOL_TO_ACTION` and resolves the asset/track against live world state; an arbitrary action string is discarded.
- **Doctrine writes are whitelisted**: `DoctrineUpdateBlock.run` (`logic_blocks.py:223-226`) only mutates `rule in doctrine["rules"]`, so the model cannot inject new doctrine keys; writes are atomic (`_atomic_write_json`).
- **Real network timeout** (`_LLM_TIMEOUT = 25 s`, passed to `ollama.chat`) and the live tactical path does **not** fall back to canned data — it returns an honest error.
- The kill itself (when it happens) is genuinely read from world ground truth, and BDA is resolver-driven, not script-set — that part of `run_e2e_proof.py`'s claim holds. The dishonesty is in attributing the *decision* to the AIP/LLM, not in faking the *physics*.
